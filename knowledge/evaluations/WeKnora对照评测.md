# WeKnora 对照评测（腾讯开源框架）

- 日期：2026-09-17
- 被测：`Tencent/WeKnora` **Lite 版**（本地已部署，`http://127.0.0.1:8080`）
- 对照对象：本项目自建检索栈（BM25 + TEI 稠密向量 + 加权融合 + LLM 重排）
- 题集：dev 20 题 / test 21 题（同一套，与自建栈完全相同的题与判据）
- ⚠ **口径提示（2026-09-29 补）**：本文导入 WeKnora 的是 **494 段语料**（中文化重组前）。现役语料为
  **1757 段 / 26 来源**，若要复用「双路召回 + 统一重排」的路线需按新语料重跑。

## 0. 先纠正一条作废数据

此前 `runs/weknora-topk.json` 里的 `0/18` **不是 WeKnora 的成绩，是判据错**：

1. 那次查询的知识库（`b3d2db99…`）里**根本没有职业语料**，只有 4 份合成测试文档 `edge_model_compression.md`；
2. 判据拿 WeKnora 返回的 UUID chunkId 与本地 `S01#s2` 式 id 精确比对，两者不同源，必然 0 命中。

**本次的做法**：把本地 494 段语料导入新库（`961b2902-2aad-4b28-a381-9132e5fff31f`，
一段一文档），并按返回项的 `knowledge_title` 前缀把结果对齐回本地 chunkId——
对齐率 100%，未对齐 0 个。

## 1. 部署与口径（影响可比性，必须先说）

| 项 | 实际情况 |
|---|---|
| 版本 | **Lite**（`RETRIEVE_DRIVER=sqlite`：FTS5 稀疏 + sqlite-vec 稠密） |
| 未启用的能力 | 图谱/GraphRAG（`NEO4J_ENABLE=false`、`ENABLE_GRAPH_RAG=false`）、其自带 rerank 模型、docreader |
| 标准版 | **未部署**：Docker 镜像拉取在本机不可达（5 个镜像共 2.72 GB） |
| 嵌入模型 | `builtin-embedding-qwen3` = Qwen3-Embedding-0.6B，**与本项目自建栈同一个模型** |
| 语料导入 | 我们的 494 段各作一个文档导入，**绕过了 WeKnora 的分块器**（否则变量是"分块方式"而不是"检索栈"） |
| `top_k` 参数 | 实测被忽略，每次返回 60–80 条；本评测按其自身排序取前 3 / 前 10 |
| 命中定义 | 取回标注参考答案所在的**那一篇**（WeKnora 会把每个导入文档再切成更细的 sub-chunk，粒度比我们细） |

导库耗时：导入 494 段 86 s；异步解析与向量化约 15 分钟（瓶颈是本机 TEI 的 CPU 嵌入吞吐）。

### 2.1 留出集 test（21 题）

| **WeKnora + 同套 LLM 重排** | **17/21 (81.0%)** | **0.3492** | **0.5238** | — | — |

| 档位 | 命中率@3 | P@3 | R@3 |

## 3. 结论

**1. 在留出集上，WeKnora 明显更好——而且差距是在"同一套重排"下复现的。**

| | 自建最佳（融合+重排） | WeKnora + 同套重排 |
|---|---|---|
| test 命中率@3 | 13/21 (61.9%) | **17/21 (81.0%)** |
| test 召回率@3 | 0.4048 | **0.5238** |
| test 准确率 P@3 | 0.2698 | **0.3492** |

差 4 题（+19pp）。开发集上两者几乎打平（20/20 vs 19/20），说明**这个差距只在干净留出集上才显出来**。

**2. 差距不在后处理，在候选池。**

| 指标 | 自建融合 | WeKnora |
|---|---|---|
| top-10 里能召回到的参考答案段 | 0.4524 | **0.5952（+14.3pp）** |
| 重排把候选转成 Top-3 的效率（R@3 ÷ R@10） | 0.895 | 0.880 |

两者的重排转化效率几乎相同（0.895 vs 0.880），**差距几乎全部来自候选池质量**：
同一个重排只能在给定候选里选，候选里没有的答案，重排也变不出来。

**3. 我们自建栈的问题被定位到具体一项：α=0.35 的融合在留出集上有害。**

融合在 test 上只有 8/21，**低于任一单路**（BM25 5/21、向量 14/21），比单路向量少 6 题。
原因是留出集以「中文问 → 英文原文答」为主，BM25 跨语言近乎失效，而 α=0.35 仍给它 35% 权重，
把好候选压了下去。这个 α 是在 14 题开发集上选的——是典型的**超参过拟合**。
WeKnora 的混合检索没有这个问题：它把两路排序按自身策略合并，留出集上 R@10 = 0.5952，高于我们融合的 0.4524。

**4. 反过来也要如实说**：WeKnora Lite 的**原始**混合检索（不加后处理）并不突出，
在 dev 上（16/20）只相当于我们的单路向量、低于我们的融合（18/20）；
它真正的优势要**配上重排**才体现出来。这与它的设计一致——检索给它更宽的候选，排序交给后续阶段。

## 4. 局限（与结论同时读）

1. **测的是 Lite，不是标准版**：图谱/GraphRAG、docreader、自带 rerank 全部未启用。标准版若跑起来只会更好，**本报告没有给出 WeKnora 的上限**。
2. **绕过了它的分块器**：我们按自己的 494 段导入，它的自适应分块优势未参与评测。
3. **命中口径偏宽**：它返回的是比我们更细的 sub-chunk，只要该 sub-chunk 所属文档是我们的参考段就算命中。
   这一定义对**双方一致**（我们的档位也按标注段判）——但粒度差异意味着两者不是严格同一种检索单元。
4. **test 仍只有 21 题**：1 题 = 4.8pp，±20pp，结论只作方向性。
5. **单次运行**：重排为 LLM 调用，测试集按纪律只跑一次。

## 5. 复算

```bash
# 1) 导入语料（幂等，已导入会跳过）
python knowledge/eval/weknora_import_corpus.py

# 2) 等异步解析完成（494/494）后，跑 WeKnora 自身检索
python knowledge/eval/weknora_eval.py --kb 961b2902-2aad-4b28-a381-9132e5fff31f \
  --questions knowledge/evaluations/questions-test.json --tag wk-test --fetch-k 50

# 3) 套上同一套 LLM 重排
python knowledge/eval/weknora_rerank_eval.py \
  --input knowledge/eval/runs/wk-test-weknora-topk.json --tag wk-test
```

产物：`runs/wk-{dev,test}-weknora-topk.json`（检索原始结果，含逐题 topAll 与对齐字段）、
`runs/wk-{dev,test}-weknora-rerank.json`（加同一套重排后的结果）、
`runs/weknora-import-state.json`（导入清单）。
