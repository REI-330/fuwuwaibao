# 查询扩展与跨语言检索缺口（2026-09-27）

针对"中文问 / 英文段"的跨语言缺口，做了一轮查询扩展实验，并在过程中定位到真正的瓶颈
**不在召回、而在术语**。以下所有数字均在 dev 34 题（20 中文层 zh + 14 跨语言层 xl）上，
语料为中文化后的 1757 段，向量模型 `Qwen3-Embedding-0.6B-onnx-int8`（1024 维）。

复跑命令：

```bash
export TEI_MODEL=Qwen3-Embedding-0.6B-onnx-int8
python knowledge/eval/query_expansion_experiment.py \
    --questions knowledge/evaluations/questions-dev.json \
    --bm25-baseline knowledge/eval/runs/q1024-dev-bm25-full.json \
    --tag dev-bilingual            # 加 --reuse-expansions 可复用已有扩展、不再调 LLM
```

## 发现 1：旧版提示词的"扩展"根本没扩展

`runs/expanded-queries.json`（2026-09-27 22:41 那次）里 34 题**新增英文词 0 个**，
全是把中文问题换个说法。旧提示词只写了一句「补上对应的英文术语」，`deepseek-v4-flash`
34/34 题全部无视。所以那次运行得到的"扩展前后完全相同"（29/34 vs 29/34）不能算证据。

给提示词加两个中英对照示例后，新增英文词变成 **10.1 个/题（零新增 0/34）**，假设才真正被触发。
工具已内置这个诊断（`expansion.meanNewEnglishTerms`），跑完必须看，否则会在毫不知情下
把"基线=实验组"当成"扩展无效"。

## 发现 2：跨语言题的瓶颈是通道选择，不是扩展

dev 分层 × 通道（无扩展，Top-3 命中）：

| 层 | bm25 | vector | hybrid (α=0.35) |
|---|---|---|---|
| xl（14 题） | 8/14 = 0.571 | **13/14 = 0.929** | 11/14 = 0.786 |
| zh（20 题） | 17/20 = 0.850 | 14/20 = 0.700 | **18/20 = 0.900** |

同一份索引里，xl 层纯向量最强、zh 层融合最强，两个方向相反。融合对 xl 层是**净损失**
（13→11）：中文查询与中文段有字面重叠，BM25 把这些中文段顶上来，把向量通道已经排到
很前的英文段挤掉。典型例子 N13：纯向量把参考答案排到**第 1 名**，融合档仍然没命中。

查询扩展只抬升了**弱通道**（xl 的 bm25 8→11），向量通道没变（13）。所以它救不了融合。

## 发现 3：扩展该只喂字面通道，且只值 +1 题

把扩展只用在 BM25 通道、向量通道保持原问题：

| 配置 | 总命中 | xl | zh | 精确率 |
|---|---|---|---|---|
| 基线 hybrid | 29/34 = 0.853 | 11/14 | 18/20 | 0.402 |
| 扩展后 hybrid | 28/34 = 0.824 | 12/14 | 16/20 | 0.392 |
| **扩展BM25 + 基线向量** | **30/34 = 0.882** | **13/14** | 17/20 | 0.392 |

"扩展BM25+基线向量"把 xl 层拉到与纯向量持平的 13/14，同时保住了融合对 zh 层的收益，
总命中 29→30。但：

- 只多 1 题，正好卡在 dev 重排档 ±1 题的波动范围内，**不构成可采纳的证据**；
- 精确率反而从 0.402 掉到 0.392，还搭上一次 LLM 调用（3.3s/题）与不可复现性。

**结论：查询扩展不采纳。** 这个方向的收益太薄，代价（每次检索都要调 LLM、结果非确定）
远超收益。

## 发现 4：真正的缺口是术语，不是召回

失败最重的跨语言题 T20/T21（问"软件质量保证分析师与测试员"这个职业在数据库/操作系统/
分析计算/图形图像软件上用什么工具、哪些是热门技术），在**两个通道都够不着**：

| 题 | 基线 BM25 | 基线向量 | 精确英文术语探针（BM25） |
|---|---|---|---|
| T20 | 未出现(>50) | 171 / 408 | **第 1 / 第 4 名** |
| T21 | 未出现(>50) | 33 / 59 | **第 1 / 第 2 名** |
| N12 | 未出现(>50) | 46 / 102 | 第 6 / 23 名 |
| N13 | 未出现(>50) | 1 / 1678 | 第 5 / 10 名 |

探针 = 人工把官方英文职业名与 O*NET 软件类别名（`Software Quality Assurance Analysts
and Testers`、`Database Software`、`Operating System Software`、`Hot Technology` …）
原样写进查询。这是**上界**（用到了参考答案的措辞，不能作为验收数字），但它证明了三件事：

1. 答案就在语料里，且 BM25 早已把 `heading + sectionPath + tags + text` 一起建索引，
   英文职业名是可字面命中的；
2. 失败纯粹是**术语没对上**，不是召回不了；
3. 泛化 LLM 扩展打不到点上——它把职业名译成单数 `analyst / tester`，而 sectionPath 里
   是复数 `Analysts / Testers`，分词器不做词干还原，字面就对不上。泛化扩展把标题拆成
   普通名词的写法对不上 sectionPath 里的官方写法。

复跑：

```bash
node knowledge/pipeline/bm25-full.mjs \
    --questions knowledge/eval/runs/_probe_title_query.json \
    --out knowledge/eval/runs/_probe_bm25.json --top 50
```

## 下一步（待拍板）

按上界结果，正确的做法是**语料内构建的双语术语词典**，而不是每次检索调 LLM：

- 从语料里抽出中英两侧的**职业名**（O*NET sectionPath 的英文标题）与**软件类别名**
  （正文里 `Configuration management software —` 这类标签），离线做一次性中英对照，
  形成可审计、可缓存的静态词典；
- 检索时：中文职业名 → 命中词典 → 把**精确英文标题**追加进 BM25 查询。确定性、无
  per-query LLM、零延迟增量。
