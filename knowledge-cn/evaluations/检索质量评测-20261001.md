# 中国官方语料知识库 · 检索质量评测（2026-10-01，三版对照）

- 题集：`knowledge-cn/evaluations/questions-cn-v1.json`（33 题：可答 26 / 超范围 7，gold 组 35 个）
- 被测对象：WeKnora Lite 知识库 `aacc4889-a347-44ea-9dd1-b60ec1917cbb`
  - **第一版（改造前）**：6 份文档（含重复的 nbs-wages-2025.md）/ 2167 chunk
  - **第二版（一块一条记录 + 删重复）**：5 份文档 / 2641 chunk
  - **第三版（现役：工资统计切到 2400 + RRF 权重 0.2/0.8）**：5 份文档 / **2612 chunk**
- 真实接口：`POST /api/v1/knowledge-bases/{kb}/hybrid-search`，`match_count=10`、`skip_context_enrichment=true`
- 证据：
  - `evidence/retrieval-quality-20261001.json`（第一版）、`…-v2.json`（第二版）、**`…-v5.json`（现役第三版）**
  - `evidence/chunking-sweep-nbs.json`（切块参数对照）、`evidence/rrf-weight-sweep.json`（融合权重扫描）
  - `evidence/questions-verified.json`（gold 复核含锚点跨度）、`evidence/boilerplate-experiment.json`（出处样板对照实验）

## 一、口径

| 项 | 定义 |
|---|---|
| gold | 锚点字符串（如 `["低空经济与管理","020110TK"]`），不用 chunkId；不受分块与重复导入影响 |
| 判定(a) 块内 | 前 k 条里存在**一条** chunk 同时含该组全部锚点 |
| 判定(b) 窗口内 | 前 k 条**合起来**含该组全部锚点（RAG 的真实形态） |
| 命中@k | **每个** gold 组都到齐才算命中；定位次取「最后一组到齐」的名次，MRR 取倒数 |
| preview@1 | 第 1 条 chunk 的前 120 字里是否含全部锚点（`verify_import.py` 的 `topPreview` 口径） |
| 超范围题 | 不做命中判定，只量分数分布 |
| judgment 组 | 作者裁定的跨源关联，不进头部指标 |

题集分布：专业目录 8、薪资统计 8、职业大典 7、跨源综合 3、超范围 7。
融合权重是**租户级配置**（`tenants.retrieval_config`），每份证据里都记了当次生效值。

## 四、第二版当时没有变好（后来靠两个后续动作补回来了）

1. **第二版的位次没有变好**：全 26 题均秩 2.77 → 2.85，未换 gold 的 23 题 2.87 → 2.83；
   @1 命中数 16/26 → 13/26，逐题**升 6 题降 4 题**（升：CN10 5→3、CN12 9→8、CN13 8→6、
   CN16 3→1、CN22 7→1、CN24 7→5；降：CN02 1→3、CN18 1→8、CN25 1→4、CN26 1→3），
   另有 3 题（CN07 / CN08 / CN19）因**标注**从单组改成多组而变严。
   当时的结论是「修的是结构问题，位次没变好也不能说变差」。
2. **后来补了两个动作，位次就上去了**（见第五、六节）：工资统计按表切块（+4 题 @1）、
   融合权重从 0.7/0.3 挪到 0.2/0.8（再 +1 题 @1，且让混合第一次超过纯关键词）。
   最终 @1 19/26、MRR 0.819，**高于改造前的 16/26、0.700**。
3. **@10 覆盖率三版都是 26/26**。这批语料从来不是「召不回来」，而是「排不准」——
   后面两个动作动的都是「排得准不准」。
4. **纯向量通道一度掉到 @1 30.8%，靠工资统计的切块补回到 53.8%**（见第五节）。

## 五、切块参数按文档扫：工资统计要「一张表一块」

不同正文形态要不同块长，所以做了 `eval/chunking_sweep.py`：**每个档位一个独立临时库**
（同一份文档的不同切块版本放进同一个库会互相竞争，名次就不可比了），
导入后只评 gold 出自该来源的题，扫完删库。**不做删除、不做整库重建**，一档几十秒。

工资统计（15.3k 字，原始 36 chunk）扫六档，9 道相关题：

| 块长 | chunk 数 | @1 | MRR | 均秩 |
|---|---|---|---|---|
| 512（原默认） | 36 | 4/9 | 0.633 | 2.44 |
| 768 | 23 | 6/9 | 0.754 | 2.00 |
| 1024 | 17 | 6/9 | 0.778 | 1.67 |
| 1600 | 11 | 8/9 | 0.944 | 1.11 |
| **2400（选定）** | **7** | **9/9** | **1.000** | **1.00** |
| 3200 | 5 | 9/9 | 1.000 | 1.00 |

**单调改善，2400 处饱和**——统计局的表按行排成竖直串，512 字会把一张表切成 2–3 块，
数字和行业名经常落在相邻但不相同的块里；2400 字刚好装下一张完整的表。

拿到正式库复跑（只重导这一份文档，其余不动）：相关的 5 道题全部从 3–8 名提到**第 1 名**
（CN10 3→1、CN12 8→1、CN13 6→1、CN15 4→1、CN26 3→1），**其余 21 题零回归**；
纯向量通道 @1 也从 30.8% 回到 53.8%。

口径提醒：块越大，「锚点落进同一条 chunk」这件事本身就更容易成立，所以这个扫描是
**偏向大块**的。两点让它没有退化成送分题：(a) 2400 时这份文档仍有 7 个语义单元（一张表一块），
不是整篇一块；(b) 非工资题完全没被带动（还是原样），说明提升来自真实的表内聚合，
不是「块大了什么都命中」。

## 六、融合权重扫描：0.7/0.3 → 0.2/0.8（对半交叉验证）

三版都出现同一个现象：**纯关键词通道一直强于纯向量**。融合权重（租户级
`retrieval_config.rrf_vector_weight / rrf_keyword_weight`，默认 0.7/0.3）既然偏向弱的那一侧，
就值得扫。改权重不用重建索引、不用重启，一档几秒钟（`eval/rrf_weight_experiment.py`）：

| 向量:关键词 | @1 | @3 | @5 | @10 | MRR | 均秩 |
|---|---|---|---|---|---|---|
| 0.7 : 0.3（原默认） | 18/26 | 21 | 23 | 26 | 0.778 | 2.12 |
| 0.5 : 0.5 | 18/26 | 22 | 24 | 26 | 0.789 | 2.00 |
| 0.3 : 0.7 | 18/26 | 22 | 24 | 26 | 0.790 | 1.96 |
| **0.2 : 0.8（现役）** | **19/26** | **23** | **24** | **26** | **0.819** | **1.85** |
| 0.1 : 0.9 | 18/26 | 23 | 25 | 26 | 0.804 | 1.81 |

MRR 在 4 档上单调朝关键词侧改善，0.2/0.8 最好，再往关键词侧压开始回落。

**这不是「在一套题上挑了个最好看的数」**：把 26 题按奇偶对半，
在 A 半上选权重 → 拿到 B 半上验证得 MRR 0.834（基线 0.781）；
在 B 半上选 → 拿到 A 半上得 0.804（基线 0.774）。**两个半边独立选出的都是 0.2/0.8**，
所以这个档位留在了租户配置里，并写进每份证据（`retrievalConfig`）以便复算。



## 七、出处样板稀释假说：测了，不成立

改造后每个 151 字（中位）的 chunk 里，仍有 **58% 是同一段出处样板**
（`_出处：… · 类型：… · 记录 ID：… · 审核状态：… · 豁免人：业主_`）。怀疑它把 862 个 chunk 的向量
挤成一团、拖垮了向量通道。于是做了个**不动索引**的对照实验
（`eval/boilerplate_experiment.py`，用同一个 8090 嵌入服务分别算「带出处」与「剥掉出处」两套向量）：

| 指标 | 带出处 | 剥掉出处 |
|---|---|---|
| 862 个 chunk 的平均两两余弦 | 0.4902 | 0.4702 |
| 目标 chunk 名次改善 / 变差 / 不变 | — | **2 / 3 / 3** |

两点结论：

- 剥掉出处只把平均相似度从 0.49 降到 0.47 —— **相似不是样板造成的，是这批记录本身长得一样**
  （850 条 `专业代码：X／专业名称：Y／第 N 页` 的模板记录）。换渲染方式救不了向量通道。
- 名次有升有降（2 升 3 降），**没有系统性收益**。所以就**没有**再做一次「精简出处行」的重建
  —— 省下一轮十几分钟的导入，也避免把「改了个没用的东西」写进交付说明。

> 插一句：这个实验顺带确认了 8090 服务的 `model` 字段不影响结果（同一个文本用两个模型名，
> 返回向量完全相同），所以用任意模型名做对照实验是有效的。

## 八、三版都要保留的结论

1. **调权重前，关键词单跑一直强于混合**（第一版 @1 65.4% vs 61.5%、第二版 57.7% vs 50.0%）。
   本题集偏字面事实（专业代码、表格数值、职业编码），关键词天然占优；这就是第六节把权重
   往关键词侧挪的动机。调完之后混合反超（19 vs 17），**但也不能因此说「向量没用」**——
   向量通道单独跑仍有 14/26，且本题集没有覆盖语义型问题。
2. **超范围题在检索层完全分不出来。** 7 道超范围题的 top-1 分数全部等于满分 0.016393
   （两通道都排第 1），可答题的 p25 是 0.016141 —— 按阈值判拒答 **7/7 误判**。拒答只能由上层
   依据「召回正文里有没有答案」来判断。
3. **剩下的弱项**只有两处：跨源语义桥接（CN25/CN26 的 judgment 组三版都没进前 10，
   语料里本来就没有那条映射）和 CN18（数字化管理师编码，长期在第 8 名——
   查询词被「数字化」抢走，而语料里这个职业只出现在目录页的编码清单里，没有独立定义段）。
4. **不得对标 `docs/EVALUATION.md` 的「人工 100 题 Top-5 ≥ 80%」门槛**：本次是作者自出的
   26 道可答题、机器复核 gold，出题人与题量都不符。

## 十、复算方式

```bash
# 1) 标注门禁（35 个 gold 组必须在真实库里找到出处，并报出锚点跨度）
python knowledge-cn/eval/verify_questions.py \
  --db knowledge-v1/weknora-src/data/weknora-cn.db \
  --questions knowledge-cn/evaluations/questions-cn-v1.json \
  --out knowledge-cn/evidence/questions-verified.json

# 2) 三通道检索评测（块内 + 窗口内两个口径）
python knowledge-cn/eval/retrieval_quality.py \
  --kb aacc4889-a347-44ea-9dd1-b60ec1917cbb \
  --questions knowledge-cn/evaluations/questions-cn-v1.json \
  --top 10 --out knowledge-cn/evidence/retrieval-quality-<日期>.json

# 3) 出处样板对照实验（不动索引）
python knowledge-cn/eval/boilerplate_experiment.py \
  --db knowledge-v1/weknora-src/data/weknora-cn.db \
  --questions knowledge-cn/evaluations/questions-cn-v1.json \
  --out knowledge-cn/evidence/boilerplate-experiment.json

# 4) 单个文档的切块参数扫描（每档一个独立临时库，跑完删库）
python knowledge-cn/eval/chunking_sweep.py \
  --file nbs-wages-2025.jsonl --source nbs-wages-2025 \
  --sizes 512,768,1024,1600,2400,3200 \
  --questions knowledge-cn/evaluations/questions-cn-v1.json \
  --out knowledge-cn/evidence/chunking-sweep-nbs.json --delete-scratch

# 5) 融合权重扫描（改的是租户配置，不重建索引；跑完恢复或 --keep-best）
python knowledge-cn/eval/rrf_weight_experiment.py \
  --kb aacc4889-a347-44ea-9dd1-b60ec1917cbb \
  --questions knowledge-cn/evaluations/questions-cn-v1.json \
  --weights 0.7:0.3,0.5:0.5,0.3:0.7,0.2:0.8,0.1:0.9 \
  --out knowledge-cn/evidence/rrf-weight-sweep.json

# 6) 整库重建（照 rebuild_weknora.py 里的参数表执行，可重复跑）
python knowledge-cn/acquisition/rebuild_weknora.py --kb-id <kb-id>
```

> 复算前先确认两件事：库是 5 份文档 / 2612 chunk（`verify_import.py`），
> 租户 RRF 权重是 **0.2 / 0.8**（`GET /api/v1/tenants/kv/retrieval-config`）。
> 第二版那批数字是默认权重 0.7/0.3 下测的，两份证据里的 `retrievalConfig` 字段可以核对。
