# 回答质量与引用支持度评测（2026-10-01）

> 这份报告补上 `检索质量评测-20261001.md` §十一 里留白的另一项：
> 「没有做「引用支持度 / 回答质量」评测（要调模型，属上层）」。

## 一、结论先说

在**偏语义 16 题**（`questions-cn-semantic-v1.json`）+ **超范围 7 题**（取自基础题集）上，
用现役配置（RRF 0.2/0.8、top-5、每条片段 2400 字上限）跑真模型 `deepseek-v4.1-flash`：

| 指标 | 结果 | 怎么算的 |
|---|---|---|
| 引用合法（回答里的 `[片段N]` 都落在本次真检到的 1..k 内） | **16/16（100%）** | 正则取引用编号，与 hit 数比对 |
| 引用支持全部 gold 组（被引用片段含该题全部锚点） | **14/16（87.5%）** | 锚点逐字包含 |
| 答案正文命中全部锚点（严格代理指标） | **12/16（75%）** | 锚点逐字包含 |
| 可答题里出现「无法回答」类表述 | **3/16（18.75%）** | 正则启发式 |
| 超范围题正确拒答 | **7/7（100%）** | 正则启发式 |

**两条最值得说的**：

1. **两个口径互相印证**：`引用支持全部 gold 组` 失分的恰好是 CN06、CN18 两题 ——
   与检索侧 `@10 窗口内 = 14/16` 未命中的**是同两题**。也就是说：
   检索说「证据没进上下文」，回答层就说「无法回答」，**没有出现「检索没命中、模型照样编」**。
2. **该拒答时拒得干净**：7 道超范围题全部拒答；两道证据真的不在上下文里的可答题也拒答。
   在「宁可不答也别编」这条上，产品侧的提示词约束是有效的。

## 二、三个口径的边界（别把代理指标当结论）

* **「答案正文命中全部锚点」是严格代理指标，不是正确率**。失分的 4 题里，CN09/CN10 的回答其实
  *引用了*含锚点的片段（`引用支持 gold = true`），只是模型把「129441 元」写成「约 12.9 万元」这类
  口径差异，于是逐字比对不中。**不要**把这 12/16 读成「四分之一答错」。
* **「拒答」靠关键词正则判定**，是启发式，不是人工评；模型绕圈子说「不确定」会被算作没拒答。
* **「回答质量」在这里只等于上面这几条机械口径**：不做流畅度/有用性/风格评价，
  也**没有请第二个模型当裁判**（那会引入「裁判与被评同源」的问题，且无法复算）。
* gold 仍是**作者标注 + 机器复核出处**，不是业主人工判定相关性。

## 三、一次值得留痕的度量缺陷（我自己踩的）

第一版脚本把每条片段**截到 600 字**再喂模型。本库的块约 **2400 字**，工资统计表的行在表格深处 ——
于是「锚点明明命中了前 5，模型却说没看到」。第一版跑出来：

```
引用支持全部 gold 组 14/16  |  答案正文命中全部锚点 8/16  |  可答题里出现拒答 8/16
```

把上限改成 2400（等同于不截断）后：

```
引用支持全部 gold 组 14/16  |  答案正文命中全部锚点 12/16  |  可答题里出现拒答 3/16
```

**「引用支持 gold」一列没变**（那一列只看原始 chunk，不受截断影响），
而「答案命中锚点」与「拒答」两列大幅变化 —— 这正好说明：
**回答层指标会被「喂进去多少上下文」独立地影响，不能与检索指标混着看。**
所以脚本把 `--snippet-chars` 做成显式参数并在证据里记下取值，默认 2400。

## 四、剩下 3 条拒答逐条说清

| 题 | 为什么拒答 | 定性 |
|---|---|---|
| CN01（2026 新设本科专业代码） | 片段里有「低空经济与管理 / 020110TK」，但**我改写时加了「与无人机产业直接相关」这个限定**，片段里没有这句话，模型据此拒答 | **题面瑕疵**（我的改写问题），不是检索或模型的问题 |
| CN06（该专业属于哪个专业类） | 含锚点（`0201 经济学类`）的块**没进 top-5**（该题在 0.2/0.8 下 @10 也漏） | **真实检索未命中**（语义题，关键词通道帮不上） |
| CN18（数字化管理师编码） | 同上；且模型指出「片段在职业名称与编码处被截断」—— 512 字块边界把一条职业记录切开了 | **真实检索未命中 + 块边界切分** |

后两条与 `语义题集与权重外推-20261001.md` 里「语义题上向量权重更高时 @10 多找回 1 题」
是同一个现象的两种观察。

## 五、复算命令

```bash
export PYTHONIOENCODING=utf-8

python knowledge-cn/eval/answer_support.py \
  --kb aacc4889-a347-44ea-9dd1-b60ec1917cbb \
  --questions knowledge-cn/evaluations/questions-cn-semantic-v1.json \
  --refusals knowledge-cn/evaluations/questions-cn-v1.json \
  --top 5 --snippet-chars 2400 \
  --model-note "deepseek-v4.1-flash（本地端点，与产品侧共用 backend/llm.py 的客户端纪律）" \
  --out knowledge-cn/evidence/answer-support-semantic.json
# 实测：23 题（可答 16 + 超范围 7），耗时约 320 s（单题约 14 s）
```

模型这一层走的是 `knowledge/eval/_shared_llm.py → backend/llm.py`，
与产品侧**同一份客户端纪律**（max_tokens 下限、瞬时失败退避重试、4xx 不重试），
不是又写一遍 `urllib`。

## 六、还没做到的（如实列出）

- **没有做人工评**：上面全部是机械口径 + 启发式，没有人工逐题看过回答是否「真的有用」。
- **没有做跨题集/跨语料复核**：只在现役中国官方语料库上跑过。
- **没有测多轮**：只做单轮问答，没有测「追问后上下文如何变化」。
